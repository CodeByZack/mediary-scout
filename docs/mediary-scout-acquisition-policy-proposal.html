4选片改 · 两处

有 A（任意数量） → 全部 A 按评分序入队，不调 AI，逐个试。

无 A → arbitrateSelection 挑最多 3 个（有序，最佳在前）或放弃。
返回的每个 id 各自过幻觉防御：不在快照内 → 按放弃处理（绝不触 SANDBOX_CANDIDATE_NOT_IN_SNAPSHOT 炸掉 run）。
挑完的起点之后，循环仍按 nextCandidate(grading, tried) 顺着 ranked 列表往下走（B/C 候选也会试）。

5转存循环 · 预算 10改 · 核心

while need 非空 ∧ 本池转存数 < 10 ∧ deadRetries < 10 ∧ 还有下一候选：

transferCandidate → digestStaging（对照当前 need）→
· 命中 ≥ 1 个 need code → 增量落库：finalizeLanding(onlyCodes=命中的码)（改名 + 归位 + markObtained）→ need 缩减 → 下一个候选
· 命中 0 个 → wipe staging → 下一个候选
· need 空 → 完成
关键机械点：need 集合在循环内可变，digest 的 needCodes 参数要跟着更新，否则后面候选的覆盖判定永远对照原始 need、永远判「未全量对齐」。

C

关键分歧 · 部分命中怎么处理

你撞到的那个问题：既不能因部分命中放弃后续完整匹配，也不能丢掉已匹配的数据

你说的那句「既不能…也不能…」其实已经把答案指出来了：「放弃后续候选」和「保留已匹配数据」在今天是被绑在一起的，因为落盘动作被强制绑定到「全量通过」这个条件上。 解法就是把这两个决定拆开——保留数据（落库）和继续尝试（换候选）本来就不冲突。

方案 1 · 增量落库 推荐

命中 ≥1 → 立即落库已命中的码 → need 缩小 → 继续试下一个候选
  • 两个决定解耦：既保留了已匹配数据，又没放弃后续候选的完整匹配机会——正是你要的
  • 零新概念：onlyCodes / skipCodes / 逐集 markObtained 全是现成机制
  • 下一次巡检的 computeNeed 自动只算剩余 need，不用管跨 run 状态
  • 重叠集数被 skipCodes 跳过，不会重复归位（也就不会撞网盘同名 (1) 复制）
  • 后一个候选的包仍要整包下载——转存是整包粒度，无法只下剩余集
  • 比现状严格更省：今天每次 wipe，下次巡检重下整包；增量落库至少已经有的不重下

方案 2 · 暂存区（hold area）

部分命中 → 移到 Season 之外的 hold 目录 → 继续试 → run 结束统一 promote
  • 不重复下载：重叠部分已在 hold 里，不用等 promote 时再搬一次
  • Season 目录一次性组装完成，不会分多次归位
  • 新增存储生命周期概念：hold 目录要在 withStagingCleanupStage 的清理范围之外（否则 run 结束被兜底清掉），失败路径要另写清理逻辑
  • 改动面明显更大：目录生命周期、清理钩子、失败回滚三处都要动
  • 没有解决分歧，只是把「落不落下」这个决定推迟到 run 结束——而那时你还是要回答同一个问题

方案 3 · 保留 §43 全量对齐

部分命中 → wipe → 换候选（现状）
  • 零误标风险：一个都不会把错内容标成 obtained
  • 你正在撞的问题不会消失——综艺按「第N期」分候选时，单个候选常常拿不齐全部 need，结果永远 reportNoCoverage
  • 每次巡检重下整包，流量与时间白费
  • 这是 AGENTS.md §9 第 3 条记的「用户 2026-09-06 明确搁置」的那个待办——你现在是在把它重新打开
必须先确认 §43 那条铁律是冲着 PR #24 中餐厅 S10E11 假入库修的。去掉它之后，防「错内容被标成 obtained」还剩三层：隐形季号闸门（标题自带季 → 降 C）、年守卫（文件名日期与播出日差 >45 天 → 不采信）、期号一致性（AI 映射的「第M期」与 TMDB Episode N 不符 → 整表作废）。
你经历过那次的具体形态：如果那包的标题里没有自带季号、播出日也对得上，那全量对齐当时就是唯一拦住它的层，方案 1 就不安全。这个只有你能判断——见 D-1。
